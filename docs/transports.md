# Транспорты: кабель и приёмник 2.4 ГГц

Документ этапов **A** и **B**.

## 1. Общая схема

Устройство предоставляет несколько HID-интерфейсов под одним VID/PID. Штатный софт открывает два:

- `hCmd` — Feature Report `0x08`, 17 байт, `HidD_SetFeature`;
- `hNotify` — Input Report `0x09`, 17 байт, overlapped `ReadFile`.

Слой `device` не должен знать, кабель это или приёмник: он получает `Transport` и `ConnectionKind`.

## 2. Что найдено статически

`FindDev` в `OemDrv.exe` перечисляет HID-интерфейсы и выбирает их по свойствам:

| Интерфейс | Условие в коде | Статус |
|---|---|---|
| `hCmd` | usage page `0xFF02`, usage `2`, Feature Report `0x08`, длина `0x11` | VERIFIED |
| `hNotify` | usage page `0xFF01`, usage `0`, Input Report `0x09`, длина `0x11` | VERIFIED |

Проверка на текущей машине (2026-10-26):

| PID | Описание Windows | Режим | Статус |
|---|---|---|---|
| `0xFA7B` | `VID_25A7&PID_FA7B` | кабель | VERIFIED по записи `startup_read_all_wired` |
| `0xFA7C` | `2.4G Wireless Receiver` | приёмник | VERIFIED по записи `startup_read_all_dongle` |

Фактические коллекции (проверено через hidapi и HID report descriptor):

| Коллекция | usage page/usage | Отчёт | Роль |
|---|---|---|---|
| `MI_01&Col05` | `0xFF01/0` | Input Report `0x09`, 16 байт данных | `hNotify` |
| `MI_01&Col07` | `0xFF02/2` | Feature Report `0x08`, 16 байт данных | `hCmd` |

Версия устройства (`bcdDevice`/`HIDD_ATTRIBUTES.VersionNumber`) на проверенной мыши: `0x1332`.

В коде также видно:

- `hCmd` открывается с доступом `0x120089`, `hNotify` — `0x120116`;
- после открытия отправляется проба Feature Report `0x08` с командой `0x03`;
- ответ ждётся на `hNotify` до 1000 мс;
- при двух найденных устройствах штатный софт отказывается работать.

## 3. Правила нашего приложения

1. Перечислять **все** HID-интерфейсы для VID `0x25A7` и PID `0xFA7B`/`0xFA7C`.
2. Для каждого логировать: путь, interface number, usage page, usage, длины input/output/feature, report ID.
3. Выбирать `hCmd` по наличию Feature Report `0x08`/длине 17, `hNotify` — по Input Report `0x09`/длине 17. Usage page — дополнительный признак.
4. Не полагаться на номер интерфейса: у кабеля и приёмника раскладка может отличаться.
5. При двух устройствах приоритет — кабель; в UI показать «USB» и предупреждение.
6. При отключении не падать: закрыть хэндлы, перечислить заново, перечитать CID/MID/версию, перезагрузить состояние.
7. При сне/офлайне — не блокировать UI, ставить запись в очередь.

## 4. Отличия кабель/приёмник

Подтверждено записями:

| Свойство | Кабель (`0xFA7B`) | Приёмник (`0xFA7C`) |
|---|---|---|
| Feature Report | `0x08`, 17 байт | `0x08`, 17 байт |
| Input Report | `0x09`, 17 байт | `0x09`, 17 байт |
| Команды | те же | те же |
| Профиль EEPROM | 106 чтений, дамп совпадает | 106 чтений, дамп совпадает |
| `diff` профилей | — | **0 различий** |
| PID | `0xFA7B` | `0xFA7C` |
| Батарея | 95%, charging=1 | 85%, charging=0 |
| `WaitNotify` | ~1030 мс | ~1030 мс |

Различий в протоколе и состоянии профиля не найдено. Отличаются только PID и поля питания.

## 6. Проверка одинаковости состояния

```
aj199ctl dump-all --out wired.json
aj199ctl dump-all --out dongle.json
aj199ctl diff wired.json dongle.json
```

Ожидается отсутствие различий, кроме:

- `connection_kind`;
- `pid`;
- `battery`;
- `charging`;
- служебных полей времени/версии.

Если diff покажет различия в профиле — это ошибка чтения или реальное различие прошивок; записать в `CHANGELOG` и разобрать по трафику.
