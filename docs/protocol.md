# Протокол AJAZZ AJ199

Документ этапов **A** и **B**. Источники:

- `OemDrv.exe` штатного драйвера — Ghidra 12.2, дизассемблирование x86;
- `Cfg.ini` штатного драйвера;
- записи USB-трафика в `local/captures/` (кабель и приёмник).

Обозначения:

- **VERIFIED** — подтверждено кодом `OemDrv.exe`, `Cfg.ini` или записью трафика.
- **HYPOTHESIS** — требует дополнительной проверки.
- **POLICY** — решение нашего приложения, а не факт протокола.

## 1. Идентификация

| Параметр | Значение | Статус |
|---|---|---|
| VID | `0x25A7` | VERIFIED |
| PID кабеля | `0xFA7B` | VERIFIED по записи `startup_read_all_wired` |
| PID приёмника | `0xFA7C` | VERIFIED по записи `startup_read_all_dongle` |
| CID | `0x40` | VERIFIED по ответу команды `0x01` |
| MID | `0x01` | VERIFIED по ответу команды `0x01` |
| Сенсор | PAW3395 (`0x3395`), до 26000 DPI | VERIFIED (`Cfg.ini`) |
| Версия прошивки | `HIDD_ATTRIBUTES.VersionNumber` | VERIFIED (код `Psd_Thread`) |
| Один экземпляр | мьютекс / один активный девайс | HYPOTHESIS |

Оба режима используют одинаковый протокол и одинаковое состояние EEPROM. Различаются PID, батарея/зарядка и, возможно, таймауты.

## 2. HID-интерфейсы

`FindDev` открывает два интерфейса, подбирая их по свойствам:

| Хэндл | Назначение | Признаки в коде | Статус |
|---|---|---|---|
| `hCmd` | команды `SetFeature` | usage page `0xFF02`, usage `2`, Feature Report `0x08`, 17 байт | VERIFIED |
| `hNotify` | уведомления `ReadFile` | usage page `0xFF01`, usage `0`, Input Report `0x09`, 17 байт | VERIFIED |

- `hCmd` открывается с доступом `0x120089`, `hNotify` — `0x120116`.
- После открытия `hCmd` штатный софт отправляет пробный Feature Report с командой `0x03` **с нулевой контрольной суммой** и ждёт уведомление на `hNotify` (таймаут 1000 мс). Устройство принимает такую пробу.
- В нормальной работе команды отправляются с корректной контрольной суммой.
- Если подключено два устройства, штатный софт отказывается работать. Наше приложение при двух устройствах отдаёт приоритет кабелю и сообщает об этом в UI (**POLICY**).

## 3. Формат кадров

### 3.1. Команда: Feature Report `0x08`

Всего **17 байт**:

| Смещение | Поле | Примечание |
|---|---|---|
| `0` | `0x08` | Report ID |
| `1` | Command ID | ID команды |
| `2..15` | Data | 14 байт данных, неиспользованные — нули |
| `16` | Checksum | `(0x55 - sum(bytes[0..15])) & 0xFF` |

Checksum **включает Report ID `0x08`**. Проверено по коду `FUN_004519f0` и по всем нормальным кадрам записей.

Исключение: проба `FindDev` — команда `0x03` с checksum `0x00`, устройство её принимает.

Отправка Feature Report повторяется до 3 раз с паузой 50 мс при ошибке `HidD_SetFeature`.

### 3.2. Ответ: Input Report `0x09`

Всего **17 байт**, читается через overlapped `ReadFile` на `hNotify`:

| Смещение | Поле | Примечание |
|---|---|---|
| `0` | `0x09` | Report ID |
| `1` | Command ID | По нему `WaitNotify` фильтрует ответ |
| `2` | Статус/результат | Зависит от команды |
| `3..15` | Данные | Зависят от команды |
| `16` | Checksum | `(0x55 - sum(bytes[0..15])) & 0xFF` |

Все 112 ответов в `startup_read_all_*` имеют корректную контрольную сумму.

### 3.3. Повторы и таймауты

- `[OPT] Retry` в `Cfg.ini`; если ключа нет — **3**.
- `WaitNotify` — около **1030 мс**.
- `GetData` для `CheckPsd`/`GetConnectStatus` — **200 мс**.
- `Match_Thread` при поиске — **1000 мс**.
- Запись EEPROM — порциями по 10 байт, пауза `Sleep(10)`; чтение — по 10 байт, пауза `Sleep(5)`.

### 4.1. Пример обмена

Чтение текущего заряда:

```
F: 08 04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 49
I: 09 04 00 00 00 02 55 00 00 00 00 00 00 00 00 00 F1
```

Для приёмника: заряд `0x55 = 85%`, charging `0`.
Для кабеля в той же сессии: `09 04 00 00 00 02 5F 01 ...` — `0x5F = 95%`, charging `1`.

### 5.3. Форматы записей

- Частота опроса (`0x00`): `[code, 0x55 - code]`.
- Количество ступеней (`0x02`): `[count, 0x55 - count]`.
- Текущая ступень (`0x04`): `[level, 0x55 - level]`.
- Параметры `0xA9..0xB7`: пары `[value, 0x55 - value]`.
- DPI (`0x0C + 4*stage`): `[x_lo, y_lo, packed, checksum]`.
- Цвет DPI (`0x2C + 4*stage`): `[R, G, B, checksum]`.
- Матрица кнопок (`0x60 + 4*key`): 4 байта кода + checksum.
- Макросы: слоты по `0x180` байт, имена в `0x301 + 0x180*index` (31 байт), данные в `0x31F + 0x180*index`; максимум 70 событий, событие 5 байт. Точная граница заголовка — HYPOTHESIS.

## 6. DPI

Для PAW3395 (`Sensor=0x3395`) формула подтверждена кодом и записями:

```
Если DPI < 26100:
    hw = DPI / 50 - 1
    mul = 0
Иначе:
    hw = DPI / 100 - 1
    mul = 1

Обратно:
    DPI = (hw + 1) * 50, если (mul & 1) == 0
    DPI = (hw + 1) * 100, если (mul & 1) != 0
```

`hw` — 10-битное значение (0..1023).

### 6.1. Упаковка ступени

```
byte0 = hw_x & 0xFF
byte1 = hw_y & 0xFF
byte2 = ((hw_x >> 8) & 0x03) << 2
      | ((hw_y >> 8) & 0x03) << 6
      | (mul & 0x03)
byte3 = 0x55 - byte2 - byte1 - byte0
```

Проверено на реальных записях:

| DPI X/Y | hw | Байты |
|---|---|---|
| 800 | `0x00F` | `0F 0F 00 37` |
| 1600 | `0x01F` | `1F 1F 00 17` |
| 26000 | `0x207` | `07 07 88 BF` |

Запись DPI 1600 → 800 в штатном софте:

```
Feature: 08 07 00 00 0C 04 0F 0F 00 37 ... E1
                       ^addr=0x0C ^len=4
```

Один и тот же кадр для кабеля и приёмника.

### 6.2. Текущее состояние

На момент `startup_read_all_*`: одна активная ступень (`0x02=1`), текущая — `0` (`0x04=0`), DPI `1600`. После записи `dpi_stage1_1600_to_800_*` в `0x0C` лежит `0F 0F 00 37` (800 DPI). После последующего сброса профиля снова 1600 DPI. Остальные ячейки `0x10..0x2B` содержат старые значения (1600, 650, 3200, 5000, 26000) и не активны, пока `0x02=1`.

## 6.3. Формат `.jmm` (макрос)

Файл `.jmm` — структура **0x342 байт**, побайтово повёрнутая вправо на 2 бита. После обратного поворота:

| Смещение | Поле |
|---|---|
| `0x00` | magic `0xFACB99A0` |
| `0x14` | имя UTF-16LE, null-terminated |
| `0x6A` | события по 8 байт: `<u16 key><u16 state><u32 delay_ms>` |
| конец | событие с `key == 0` |

`state = 1` — нажатие (key down), `state = 0` — отпускание (key up). Это подтверждено поведением OEM: макрос `abc.jmm` содержит только `state = 1`, валиден и воспроизводится мышью; OEM допускает удаление key-up событий. `state & 2` — событие колеса. Для записи файла OEM поворачивает каждый байт вправо на 2; для чтения — влево на 2.

Текущий `fixtures/abc.jmm` раскодировался так:

```
Name: abc
Events:
  Space              key=0x0020 state=down delay=8 ms
  Left Ctrl          key=0x00A2 state=down delay=0 ms
```

Оба события — нажатия, key-up удалены. Это допустимый OEM-макрос: при воспроизведении мышь нажимает Space и левый Ctrl. Имя `abc` не соответствует содержимому — вероятно, файл записан не с теми клавишами, но формат корректен.

Разбор: `python tools/re/parse_jmm.py fixtures/abc.jmm`.

## 7. Кнопки

`KM=12`; формат `Kn_1 = <funcType>,<code>,<param>,<matrixIndex>`. Матрица: `0x60 + 4*key`.

Фактические значения из записи:

| Адрес | Байты | Hardware code | Вероятное назначение |
|---|---|---|---|
| `0x60` | `01 01 00 53` | `0x0101` | левая кнопка |
| `0x64` | `01 10 00 44` | `0x1001` | вперёд |
| `0x68` | `01 04 00 50` | `0x0401` | средняя |
| `0x6C` | `01 08 00 4C` | `0x0801` | назад |
| `0x70` | `01 02 00 52` | `0x0201` | правая |
| `0x74` | `06 05 fe 4c` | macro | макрос (id 5, флаг `0xFE`) |
| `0x78` | `04 0a 03 44` | `0x030a04` | неизвестно |
| `0x7C` | `08 00 00 4d` | `0x000008` | неизвестно |
| `0x80` | `07 00 00 4e` | `0x000007` | неизвестно |
| `0x84` | `02 02 00 51` | `0x000202` | DPI+ (подтверждено) |

В стартовом профиле `0x74` был макрос (`06 05 FE`). При переназначении кнопки OEM записал `02 02 00 51` — hardware-код `0x202` (DPI+); это подтверждено записью `button_dpiplus_dongle.pcap` и уведомлениями `0x0A` при нажатии. Первые пять кнопок совпадают с `Cfg.ini`.

Известные hardware-коды: left `0x101`, right `0x201`, middle `0x401`, forward `0x1001`, back `0x801`, DPI+ `0x202`, DPI− `0x302`, DPI loop `0x102`, disable `0`, macro `0xFE0506` (id 5, flag `0xFE`).

## 8. Подсветка

Основной LED: `0x4C`, логотип: `0x54`. В `startup_read_all_dongle.pcap` было:

```
0x4C: 00 55 80 d5 03 52 00 55
0x54: ff 00 ff 57 00 55 80 d5
0x5C: 03 52 00 55
```

Запись `led_breathing_red_dongle.pcap`:

```
0x4C len 6: 02 53 80 d5 03 52   // mode=2, speed=0x80, brightness=3
0x2C len 4: ff 00 00 56         // R=255, G=0, B=0 (цвет ступени DPI 1)
```

Формат `0x4C`: три пары `[value, 0x55-value]` — mode, speed, brightness. Четвёртая пара `0x52` в этой прошивке не менялась. Цвет основного LED в этой записи OEM записал в цвет текущей ступени DPI (`0x2C + 4*stage`); связь «LED цвет = цвет DPI» пока **HYPOTHESIS**, но запись `0x2C` подтверждена.

## 9. Макросы

- Форматы штатного софта: `.jmm`, `.jma`.
- Аппаратный лимит: до **70** событий; событие — **5 байт**.
- Структура события (по `StMacro_To_HdMacro`):
  - byte0: flags (`0x40/0x80` — up/down, биты 0–2 — тип ключа);
  - byte1: hardware code;
  - byte2: ноль;
  - byte3: задержка, старший байт;
  - byte4: задержка, младший байт.
- `MacroHasMsKey=0x07`, `MinDelay=1`.
- Слоты: `0x300 + 0x180*index`; `+0x00` длина имени, `+0x01` имя, `+0x1F` count, `+0x20` события.

Запись `macro_simple_abc_dongle.pcap` (макрос id 5, слот `0x300 + 5*0x180 = 0xA80`):

```
0xA80 len 10: 06 61 00 62 00 63 00 00 00 00   // длина имени 6, "abc" в UTF-16LE
0xA8A len 10: 00 ...
0xA94 len 10: 00 ...
0xA9E len 10: 00 02 81 2C 00 00 08 80 01 00   // начало данных макроса
0xAA8 len 6:  00 00 1D 00 00 00
0x074 len 4:  06 05 FE 4C                     // кнопка: macro, id 5, флаг 0xFE
```

Слот макроса `i`: `0x300 + i * 0x180` (для id 5 это `0xA80`).

| Смещение | Поле |
|---|---|
| `+0x00` | длина имени в байтах UTF-16LE, 0..30 |
| `+0x01` | имя UTF-16LE, до 15 символов |
| `+0x1F` | число hardware-событий, 0..70 |
| `+0x20` | события по 5 байт: `[flags, hid, 0, delay_hi, delay_lo]` |

`flags = ((state & 1) + 1) * 0x40 | kind`; `kind=0` — специальная клавиша, `1` — обычная HID-клавиша, `4` — медиа, `5` — колесо. `delay` — 16 бит, hi/lo. Для state=1 (нажатие) flags `0x80/0x81`, для state=0 (отпускание) — `0x40/0x41`. Таблица software key → HID лежит в `OemDrv.exe` по VA `0x5B2EB8`, 0x68 пар `(hid, key)`.

Подтверждено записью: имя можно переписать 31 байтом `[len, UTF-16LE name, 0...]`; назначение на кнопку — hardware-код `(flag << 16) | (macroId << 8) | 0x06`. В примере `flag=0xFE`. Формат событий разобран и реализован в `SoftwareMacro` (`aj199-protocol`).

## 10. Профили и питание

- `SetCurProfile` — команда `0x10`, payload `[0x10, 0,0,0, 1, profile]`.
- `GetCurProfile` — команда `0x0E`, ответ 10 байт.
- Питание — команда `0x04`: `report[6] = 0..100`, `report[7] = charging`.
- Версия прошивки — `HIDD_ATTRIBUTES.VersionNumber`, отдельной команды нет.
- `ShowPower=3` — показывать заряд и зарядку.

## 12. Открытые вопросы

1. Семантика `report[2]` и полей команды `0x03`.
2. Назначение адресов `0xAB`, `0xAD`, `0xB3`, `0xB5`, `0xB7`.
3. Точная связь цвета LED и цвета ступени DPI.
4. Полный список функций кнопок, кроме подтверждённых left/right/middle/forward/back/DPI+/DPI−/DPI loop/disable/macro.
5. Формат событий макроса после `0xA9E` и лимит.
6. Команды `0x05`, `0x06`, `0x0A`–`0x0D`, `0x0F`; `0x09` — сброс профиля.
7. Отсутствующие в GUI настройки: Motion Sync, sleep, XY Independent, sleep/wake.

## 13. Ограничения

- Прошивка и bootloader не затрагиваются.
- Запись включается только после бэкапа и проверки чтением.
- Бинарники, скины и графика OEM-софта в поставку не включаются.
